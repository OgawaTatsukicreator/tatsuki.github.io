01

アプリケーションの概要

「マソ君の日常」は、筋トレ記録と2Dキャラクター育成を組み合わせたWebアプリです。重量・回数・セット数からトータルボリュームを自動計算し、成果を育成ポイントやアイテムを通じて「マソ君」の成長へ反映します。

ホーム、記録カレンダー、トレーニング入力、履歴分析の画面を用意しています。現在の記録データはブラウザ内に保存しており、Supabaseによる認証とデータベースの下地まで作成済みです。

創った背景

一般的な筋トレ記録アプリは数値管理が中心で、入力そのものが作業になりがちです。特に記録習慣のない人は、重量や回数だけでは成果を実感しにくく、継続する理由を見失いやすいと考えました。

そこで、育成ゲームが持つ成長と報酬の楽しさを筋トレ記録へ取り入れました。自分がトレーニングを続けるほどマソ君も成長する仕組みにし、記録を義務ではなく、次の変化が楽しみになる体験へ変えることを目指しています。

現在地

主要機能はWebで公開済みです。記録データのクラウド保存は、次の段階として進めています。

02

主要ユースケースと設計意図

記録を続けたいのに、数字だけでは手応えを得にくい人を中心に据えました。トレーニング直後の短い時間で入力を終え、その場で成長を受け取れる体験を設計しています。

Who誰が
筋トレを習慣にしたい人 始めたばかりの人や、数値の記録だけでは成果を実感しづらい人を想定しています。
Whenどんな場面で
種目を終えた直後に ジムでセットを終えたときや、帰宅後にその日の内容を振り返る場面を想定しています。
What何をするのか
記録し、成長を確かめる 種目・重量・回数・セット数を入力し、自動計算された成果とマソ君の変化を確認します。

Design intent

「記録した直後に、成長が返る」短い循環

入力の先にある報酬を遠ざけないため、記録、計算、育成反映をひと続きにしました。利用者は数値を管理するだけでなく、今日の行動がどんな変化につながったかを、その場で理解できます。

  • 迷わせない必須入力を種目・重量・回数・セット数に絞る
  • 待たせない入力中からトータルボリュームを自動計算する
  • 続けたくなるポイントとキャラクターの変化で努力を可視化する

05

技術選定の理由

Frontend architecture

Next.js 16 / React 19

要件・制約ホーム、カレンダー、入力、分析の4画面で、同じ記録・育成状態を共有する必要がありました。将来の認証・クラウド保存にも無理なく広げられる構成が条件でした。

比較した案単一HTMLとVanilla JavaScript、クライアントだけで完結するReact SPAも検討しました。

選定理由Reactで画面部品を再利用し、Next.jsでルーティングとレイアウトを一貫して管理できるためです。今後サーバー側の処理を追加するときも、同じ基盤のまま拡張できます。

Language

TypeScript

要件・制約重量・回数・単位・日付・50段階の育成状態など、形の異なるデータを複数画面で安全に受け渡す必要がありました。

比較した案JavaScriptとJSDocによる型注釈も候補にしました。

選定理由データ構造を型として共有し、項目の追加や計算ロジックの変更時に不整合を開発中に検出できるためです。記録と育成状態の食い違いを減らせます。

UI styling

Tailwind CSS 4

要件・制約ジムでも片手で使えるスマートフォン中心のUIを、画面間で余白や状態表現を揃えながら短い周期で調整する必要がありました。

比較した案プレーンCSSとCSS Modulesを比較しました。

選定理由レスポンシブ指定とデザイン値を画面部品の近くで管理でき、試作中の調整が速いためです。共通の尺度を使うことで、画面ごとの見た目のばらつきも抑えられます。

Backend

Supabase

要件・制約利用者ごとの認証と記録の分離、日付や種目を軸にした集計が必要です。一人で開発するため、認証基盤と独自APIをすべて構築する負担は抑えたいと考えました。

比較した案Firebaseと、独自API＋PostgreSQLの構成を比較しました。

選定理由Auth、PostgreSQL、RLSを一つのサービスで扱え、リレーショナルな履歴分析とユーザー単位のアクセス制御を両立しやすいためです。現在はブラウザ内保存で操作を検証し、接続情報がなくても開発を進められるようにしています。

Validation

Zod

要件・制約重量・回数・セット数の上限や未来日、メモの文字数などを、実行時にも同じ規則で検証する必要がありました。

比較した案画面ごとの手書き条件分岐とYupを比較しました。

選定理由検証ルールをスキーマとして一か所にまとめ、TypeScriptの型とつなげやすいためです。画面ごとの検証漏れを防ぎ、利用者へ返すエラーも揃えられます。

Test

Vitest

要件・制約ボリューム計算、kg・lb換算、育成ポイント、経験値、日付処理は、小さな変更でも結果が連鎖して変わるため高速な回帰確認が必要でした。

比較した案Jestと、ブラウザ操作だけで確認するE2Eテスト中心の構成を比較しました。

選定理由TypeScriptの設定と合わせやすく、計算ロジックを画面から切り離して素早く実行できるためです。主要な計算18件を単体で確認し、E2Eテストは公開前の次段階に分けています。

06

工夫した点

01

筋トレの成果を育成体験へ変換

トータルボリュームを表示するだけでなく、育成ポイントやアイテムを介してマソ君の成長につなげました。

02

スマートフォンで記録しやすい導線

画面下部からホーム、記録、分析へ移動できます。入力中はトータルボリュームをその場で確認できます。

03

入力ミスと二重保存への対策

未来日の記録、入力値の上限、メモの文字数を検証。リクエストIDを使い、同じ記録の二重保存も防ぎます。

04

計算処理を画面から分離

ボリューム、kg・lb換算、育成ポイント、経験値、日付処理を分け、単体で検証できる構成にしました。

05

50段階の変化を視覚化

レベルに応じてキャラクター画像を切り替え、呼吸、まばたき、レベルアップ時の動きをCSSで加えています。

07

現時点の改善点

  • 01

    トレーニング記録、設定、育成状態をSupabaseへ保存する処理を接続する。

  • 02

    ブラウザ内の既存データを、ログイン後にクラウドへ移行できるようにする。

  • 03

    複数ユーザーを使い、RLSによるデータ分離を結合テストで確認する。

  • 04

    記録の編集・削除と、それに伴う育成ポイントの差分調整を実装する。

  • 05

    自重種目と有酸素運動の計算、週別・月別の分析を追加する。

  • 06

    公開版のE2Eテストと性能計測を行う。
